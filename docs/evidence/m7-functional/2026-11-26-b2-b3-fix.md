## B2: a new upload stuck on "Not searchable"

**Cause (confirmed).** `DocumentService.visible()` and `get()` (`backend/app/documents/ingest.py`) build each entry from several statements in one READ COMMITTED transaction: the document row (`active_generation`), then the access checks, then `list_versions` (`status`). The ingestion runner sets `active_generation` and `status = 'ready'` in one transaction. When that commit lands between the first and the last read, the entry is `status: "ready"` with `searchable: false`. `DocumentsPanel` polls only while a status is `queued`, `parsing` or `indexing`, so it stops on that mixed state and keeps "Not searchable" until the page is reloaded.

The new integration test forces that interleaving deterministically. It holds a job just before activation, then commits the activation from inside the request, between the two reads. With the fix disabled (`snapshot` ignored in `tenant_transaction`) both endpoints return exactly the demo state:

```
E       AssertionError: assert ('ready', False) == ('indexing', False)
2 failed, 1 passed, 22 deselected, 1 warning in 5.24s
```

**Fix.** `tenant_transaction(..., snapshot=True)` starts the transaction with `SET TRANSACTION ISOLATION LEVEL REPEATABLE READ`, so every statement sees one snapshot. `visible()` and `get()` use it. The list now reports the commit as either not yet applied (still in progress, so the UI keeps polling) or fully applied (`ready`, `searchable: true`). No frontend change was needed. Nothing else changes: a document with sharing not set is still `ready` / `unknown` / not searchable, a failed ingestion is still `failed` with its error, and a reader whose access was revoked no longer sees the document (list) and gets 404 (detail).

**Regression tests** (`backend/tests/integration/test_documents_ingestion.py`):

- `test_activation_committing_mid_request_is_never_reported_ready_but_unsearchable[list|detail]`
- `test_unsearchable_states_are_still_reported`: sharing not set, failed ingestion, revoked reader.

## B3: a contract answer shows the SQL-report warning

**Cause (confirmed).** `verificationText()` in `ReportPanel.tsx` recognised only the document label and `narrative == "verified"`. Everything else fell through to the SQL report's warning. The legal pack sends `legal_facts_extracted_and_rechecked` and no `narrative`, so a verified contract answer showed *"Figures verified exactly against the query result. No written summary is shown because it could not be verified."*

**Fix.** `verificationText()` moved to `apps/web/src/verification.ts`. The legal label now gets its own line, built from the checks the legal workflow runs (`backend/app/legal/workflow.py`, `verify()` and `verification()`): *"Every statement cites an exact passage of a contract you can access (re-checked at publication). Dates, terms and notice periods were re-derived from those passages by fixed rules; no model was used."* The sales report messages (verified, and each withheld reason) and the document message are unchanged. Code answers inherit the document label (`backend/app/code/workflow.py` calls `super().verification()`), so they were not affected. A label the UI does not know now gets a neutral warning instead of the SQL text.

**Regression tests** (`apps/web/test/verification.test.ts`, run with `npm test -w @eaios/web`, now also in the CI frontend job): the legal payload exactly as the backend sends it, the SQL verified line and all four withheld lines, the document line, an unknown label, and no verification block. With the legal branch disabled, the legal and unknown-label tests fail (2 of 5).
