# ADR 0601 — Email drafts, human approval and the Mailpit outbox

Status: Accepted for M6 (pending planning review). Relates to: FR-08, FR-10 (Mailpit), FR-11, NFR-01, roadmap "M6 delivery semantics" and the "Email duplicate prevention" correction. Implementation: `backend/app/actions/`, `backend/app/api/actions.py`, `backend/app/tasks/actions.py`, migration 0012, `apps/web/src/ActionsPanel.tsx`.

## Decision

1. **Source.** A draft is built only from a *published verified sales report* owned by the caller (`report_runs.status = published`, kind `report`). The body is rendered from the stored `result` (typed table cells, verified narrative, verification label, evidence id and hash), never from retrieved document text or unpublished model output. `source_sha256` (canonical JSON of the result) is stored and rechecked at approval, send and dispatch. Document, legal and code answers are not email sources in this version.
2. **Recipients come from authoritative records.** The request names a `recipient_user_id`; the server resolves it against `users` of the caller's tenant (RLS) and stores that address in the version. Request bodies with any extra field (`recipient_email`, `tenant_id`, `owner_user_id`, …) are rejected (`extra="forbid"`). A recipient must be active and must pass the same current authorization the sender needs for the source content (`dataset.query` through the five-layer policy). The address is compared with the current user record at approval, send and dispatch; a change blocks the send (`recipient_changed`). `GET /actions/recipients` lists active users of the tenant for the user's explicit choice.
3. **Versions are immutable.** `email_draft_versions` rows cannot be updated or deleted (trigger, and the app role has no UPDATE grant). An edit inserts version *n + 1* with `edited_by`, requires the caller to name the version and hash they edited (`409 version_conflict` otherwise), invalidates any active approval and returns the action to `draft`. `draft_sha256` covers tenant, action, version, recipient id and address, subject, body and source hash; it is recomputed before approval and before dispatch (`draft_integrity`).
4. **Approval binding.** `POST …/approve {version, draft_sha256}` re-runs every check and returns a one-time token (`secrets.token_urlsafe(32)`). Only its SHA-256 is stored, with the action, version, draft hash, actor user, session id and expiry (`ACTION_APPROVAL_TTL_SECONDS`, default 900 s). One active approval per action (partial unique index). The approver must be the draft owner in the same session. `POST …/send {version, draft_sha256, approval_token}` rejects, with `409 approval_rejected` and an audit reason: unknown or forged tokens and other tenants' tokens (`approval_unknown`; RLS hides them), a token for another draft (`approval_mismatch`), another user or session (`approval_actor`), a used token (`approval_used`), an invalidated token or a version/hash that differs from the approved one (`approval_superseded`), and an expired token (`approval_expired`). Another user's or tenant's draft id returns 404.
5. **Send-time checks.** In the transaction that consumes the approval and inserts the outbox row, under the tenant policy-epoch share lock (`lock_tenant_policy_epoch()`, as at report publication), the server re-reads: sender active, tenant active, `actions` pack and `mailpit` connector enabled, source run still published and authorized for the sender, source hash unchanged, recipient active, address unchanged, and recipient authorized for the content. A failure invalidates the approval, returns the draft to `draft` with the reason, and answers `422 action_blocked`; nothing is queued.
6. **Durable outbox.** `email_outbox` has one row per action ever (`UNIQUE (tenant_id, action_id)` and `UNIQUE (tenant_id, approval_id)`). `execution_key` (UUID) is the unique execution identity; the RFC 5322 `Message-ID` is `<execution_key@MAIL_MESSAGE_ID_DOMAIN>` and is reused for every attempt.
7. **Dispatch.** The worker claims a `pending` row under a row lock and the policy-epoch lock, re-runs every check in item 5 plus approval/version/hash consistency, and commits `dispatching` (attempt + 1, `claimed_at`) **before** opening SMTP. A failed re-check sets `blocked` with the reason. The SMTP exchange is driven step by step so the outcome is classified by protocol phase (`app/actions/mail.py`):
   - failure before `DATA` was sent, or an explicit 4xx reply → `not sent`: back to `pending`, retried with the same key;
   - explicit 5xx reply → `failed` (`smtp_rejected`);
   - `250` after the body → `delivered`, `smtp_accepted_at` and `confirmed_at` recorded;
   - timeout or disconnect after the body was handed over → **`uncertain`** (`smtp_ambiguous`).
8. **Crash recovery and reconciliation.** A `dispatching` row older than `EMAIL_DISPATCH_LEASE_SECONDS` (default 120, much longer than the 10 s SMTP timeout) may have crashed anywhere, including after Mailpit accepted the message: it becomes `uncertain` (`dispatch_lease_expired`), never `pending`. An `uncertain` row is reconciled by looking up its Message-ID and recipient through Mailpit's HTTP API: found → `delivered` (`reconciled_found`, `mailpit_id` stored), no resend; absent `EMAIL_RECONCILE_ABSENT_CHECKS` times in a row → `pending` (`reconciled_absent_retry`); Mailpit unreachable → stays `uncertain`. A retry claim (attempt > 0) looks Mailpit up once more before sending, and re-runs every access check. Attempts are capped (`EMAIL_MAX_ATTEMPTS`, then `failed`). A late confirmation from a slow worker is accepted only for its own attempt number. The Celery beat task `process_due_actions` (30 s) re-dispatches pending rows, expires leases and reconciles; workers discover only ids through `action_work_due()` (SECURITY DEFINER) and do all reads and writes under tenant RLS.
9. **Cancellation.** The owner can cancel a draft, an approved draft, or a queued send whose outbox row is still `pending`; once claimed it is too late (`409 too_late`).
10. **Visibility.** `GET` on a draft rechecks the viewer's access to the source report; without it, subject and body are withheld (`content_withheld: true`), as for run replay and evidence. Every step is audited (`action.email`: draft, edit, approve, send, deliver, plus every denial with its reason, recorded in its own transaction so it survives the rollback of the refused request). Tokens and message bodies are never logged.

## What this does not guarantee

Local deduplication (unique execution key, one outbox row per action, row-locked claims) prevents duplicate *application* sends. It is not an end-to-end exactly-once guarantee. Reconciliation works here because Mailpit exposes what it accepted; a real SMTP relay offers no such lookup, and a message handed to a remote server cannot be recalled. If a worker stalls longer than the lease and then completes its SMTP exchange after recovery has re-queued the row, two copies are possible; the lease is set far above the SMTP timeout to make this unlikely, and the late worker's confirmation is discarded. Already delivered email cannot be revoked by later permission changes.
