# ADR 0302 — Parsing and chunking for M3

Status: accepted for M3, pending planning-agent review. Source: M1 parser comparison (`ml/parser-benchmark/reports/2026-11-20-parser-comparison.md`), specification §9 "Document extraction" and "Chunking strategies". Implementation: `backend/app/documents/parsers.py`, `canonical.py`, `chunker.py`, `ingest.py`; gateway `ml/model-gateway/gateway.py` (`POST /parse`) and `docling_worker.py`.

## Decision

- **PDFs go to Docling on the gateway** (M1's choice for complex PDFs): `POST /parse` runs the M1 Docling environment (`colab-docling-pins.txt`, docling 2.151.1, default pipeline: layout model, TableFormer, OCR) in its own venv as a subprocess per document, on the CPU by default so it does not compete with vLLM for the T4. The worker converts Docling's reading-order items into the canonical element contract: headings with their section path, paragraphs, list items, tables as `a | b` rows with the header row's end recorded; page headers and footers are dropped. The backend validates the payload (`elements_from_docling`) and builds the canonical text exactly as for every other parser.
- **Documented fallback.** If Docling is unavailable (gateway not configured, unreachable, timed out, failed, or a malformed result), ingestion uses the local text-layer parser and records `parse_notes.docling = "unavailable: <reason>"` and `parse_notes.fallback`; a scan then becomes `needs_ocr`. M1 recommended PyMuPDF heuristic text as that fallback; M3 uses **pdfplumber** (also measured in M1; digital text 95.6, ruled tables only) rather than PyMuPDF. PyMuPDF 2.1 hard-depends on `onnxruntime` and a layout model, which would put a model runtime in the backend image against the no-models-on-laptops rule, and it is AGPL-licensed. pdfplumber makes no claims about borderless tables or multi-column reading order (M1 measured 64.7 order on the two-column page). PDFs without a text layer are `needs_ocr` and are not indexed.
- CSV uses Python `csv` (BOM, strict UTF-8, then cp1252; Sniffer; fields as text) and XLSX uses openpyxl cached values, exactly as M1 recommends. Hidden sheets are **not indexed** and are listed in the parse notes; formulas are not indexed. Markdown and plain text use a built-in parser.
- Every parser emits typed elements, joined into one **canonical text** (NFC, `\n`, blank line between elements) with each element's code-point span.
- **Chunking** is deterministic, header-aware and recursive: paragraphs under one heading path are packed up to 700 code points; longer elements split at sentence ends, then whitespace; tables stay whole or split into row groups that repeat the header in a `prefix`. A chunk's citable span is contiguous canonical text; the prefix (section path, repeated header) is context only.

## Consequences and open items

- **Parsed once per version.** The element spans are stored with the version (`document_versions.elements`, migration 0006; immutable once set, like the canonical text). Retries and reindexing rebuild the canonical document from the stored text and spans (its SHA-256 is rechecked) instead of re-parsing, so citation offsets never move, a Docling-parsed version stays Docling-parsed when Docling is later unavailable, and Docling's non-determinism cannot trigger `parser_changed`.
- Admins see each version's parser and parse notes in the document detail, so a fallback parse is visible and can be fixed by uploading a new version once Docling is back.
- Measured through the application against the M1 gold: see `docs/evidence/m3/`.
- 700 code points is a heuristic for the specification's 350-token budget. Exact checker token counts are enforced by the gateway, which refuses pairs over 512 tokens instead of truncating.
- The M1 fixtures are synthetic; the parser choice still needs confirming on real NileTech documents.
