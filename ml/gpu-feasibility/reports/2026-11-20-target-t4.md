## Load, cancellation and restart at 0.75

* **Concurrent:** 4 chat requests ran while BGE-M3 and the checker were also running (207 aux operations, no errors). The wall time was 104.8 s, and aggregate throughput 4.4 tokens/s. Per request, time to first token was 0.7 s for one and about 17.7 s for the other three, and totals ranged from 46 to 105 s.
* **Cancellation:** the client closed an unfinished stream after 20 chunks (5.5 s). `vllm:num_requests_running` returned to 0 within 0.28 s, and the follow-up request succeeded.
* **Restart:** vLLM was stopped and started again with both aux models still resident. It was ready in 78.1 s, and the first chat afterwards took 8.9 s.

## Reporting fixes made after this run

* **OOM evidence lost on restart.** The notebook took `server_log_facts` from the last vLLM server only, so the restart's clean log hid the OOM in the original 0.85 log. Each configuration now keeps the facts from every server's log (`server_logs`), and `config_oom()` counts an OOM in any of them.
* **Engine errors counted as answers.** When the engine died, vLLM sent an `error` event inside each of the 4 concurrent streams. The client ignored those events, so the 0.85 concurrent stage was recorded as "ok" with 0 tokens. Streams that carry an error event, or end without a `finish_reason`, now raise an error. That stage is still marked "ok" in this run's saved results; the OOM verdict above does not depend on it.

## Limits

* The checker is a public zero-shot NLI checkpoint used as a development baseline. Its smoke agreement of 16/20 with the expected labels is not an accuracy result.
* Generation uses fixed evidence, and the generated SQL is not executed.
* This is a single run on a single free-tier T4. Timings on other runtimes may differ.
